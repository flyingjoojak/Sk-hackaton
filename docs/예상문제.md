# 예상 문제 10개 (예측, 공식 아님)

SK hynix AI Hackathon 2026 파이널을 기업 간 거래관계·기업정보 분석으로 가정한 **예측**이다. 주최 문제가 아니고, 출제 범위도 아니다. 당일 문제 문장이 다르면 그 문장을 따른다.

각 문제는 조달·협력사 관리 TL 이 하루 안에 의사결정에 쓰려는 장면이다. 데모는 한 사람이 Codex 와 6시간(360분)에 끝내는 크기다. 공통 컷:

- 0~45분: 과제 문장, 열 이름, 담당자 질문, TASK.md. 코드 금지.
- 45~150분: MVP. 입력 CSV 에서 표 하나와 파일 출력까지.
- 150~240분: 경계값 테스트, 독립 검사기. 240분에 기능 추가 중지.
- 240~300분: 화면은 표 하나, 시나리오 한 번.
- 300~360분: 동결, README, 서술형(사실 > 결정 > 근거 > 한계).

스택은 CSV + Python 표준 라이브러리. networkx 가 있으면 중심성 대조만. Neo4j, 크롤링, 학습 모델은 하지 않는다. 참고 코드는 `tools/graph_ref.py` 를 베끼지 말고 구조를 본 뒤 다시 짠다.

## 1. 협력사 부도 시 영향 라인·자재

**문제 한 줄.** 협력사 한 곳이 오늘 멈추면, 어느 자재와 어느 하위 협력사·납품 경로가 막히는지 깊이별로 보여 준다.

**현업 맥락.** TL 은 부도 소식을 듣고 라인 중단 가능 자재를 당일 안에 추려 대체 발주를 걸어야 한다. 놓치면 라인이 서고, 잘못 잡으면 엉뚱한 자재에 인력을 쓴다. 놓치는 쪽이 더 나쁘다고 가정하고, 그 가정은 담당자에게 확인한다.

**입력 데이터.** `companies.csv`(company_id, name, country, industry), `transactions.csv`(buyer_id, supplier_id, product, amount, period). 금액 단위와 기간은 과제 원문만 사실로 적는다.

**정식화.** 공급 방향 supplier → buyer. 중단 기업을 깊이 0으로 두고, 그 기업이 공급하는 구매자를 깊이 1, 그 구매자가 공급하는 곳을 깊이 2로 BFS. 각 노드의 손실 금액은 끊긴 직접 거래 금액 합. 간접 금액은 더하지 않는다(이중 계산).

**데모 (360분).** 위 공통 시간표. MVP 는 협력사 ID 하나를 넣어 깊이, 기업, 자재, 손실 금액 표를 찍는 것. 150분 이후 자재별로 묶고, 240분 이후 화면 표. 대체처 추천은 문제 2로 미룬다.

**검증.** 기업 4~6곳의 손계산과 비교. 검사기는 생성 함수를 부르지 않고 BFS 를 다시 짜서 집합이 같은지 본다. 없는 ID, 금액 0, 자기 거래는 오류로 남긴다.

**이 저장소.** `tools/graph_ref.py` 의 `propagate`, `docs/기업분석_알고리즘_대비.md` 2절, `docs/거래관계_온톨로지.md` 의 Transaction.

## 2. 단일 공급처 의존 자재와 대체처

**문제 한 줄.** 자재별로 공급처가 하나이거나 비중이 기준 이상인 구매를 찾고, 같은 자재를 이미 파는 다른 기업을 금액 순으로 제안한다.

**현업 맥락.** 단일 소싱 자재는 협상력도 없고 중단 시 대체 리드타임이 없다. TL 은 의존 목록과 "지금 거래는 없지만 그 자재를 공급하는 회사"를 함께 본다.

**입력 데이터.** 문제 1과 같은 두 CSV. 기준 비중은 과제에 없으면 담당자에게 묻고, 답이 없으면 1.0(오직 한 곳)만 필수로 한다. 0.8 은 개선.

**정식화.** 구매자·자재별 공급 금액 비중. 비중 >= 기준이면 의존. 같으면 포함한다. 대체처는 같은 product 를 다른 구매자에게 공급한 기업 중 제외 대상과 자기 자신을 빼고, 공급 금액 합 내림차순, 동률이면 company_id.

**데모.** MVP 는 의존 목록만. 150~240분에 대체처 열과 기준 0.8 경계 테스트. 화면의 추천 문장은 규칙으로 만들고 LLM 은 쓰지 않는다.

**검증.** 80 대 20 이면 HHI 와 별도로 비중 0.8 이 경계에 걸리는지. 대체처가 없는 자재는 빈 목록과 문구. 검사기가 의존 집합을 원본 합계로 다시 센다.

**이 저장소.** `graph_ref.py` 의 `single_source`, `alternatives`. 알고리즘 문서 3절.

## 3. 수출통제·지정학 리스크 영향 기업

**문제 한 줄.** 특정 국가의 기업이 공급을 멈추는 통제 시나리오에서, 직접·간접으로 막히는 기업과 자재를 표시한다.

**현업 맥락.** 국가 단위 수출통제가 뜨면 그 국가 협력사만이 아니라, 그 협력사에게 의존하는 국내 2차도 멈춘다. TL 은 "우리 1차 중 누가 그 나라에 물려 있나"를 당일 보고한다.

**입력 데이터.** companies.country, transactions. 통제 국가 이름은 입력값. 기업 국적가 비어 있으면 제외하지 말고 `확인 필요` 로 따로 센다.

**정식화.** 해당 국가 기업 집합을 동시에 중단으로 두고 문제 1의 전파를 반복한 뒤 합친다. 국가 문자열이 다르면(대한민국 / KR) 담당자에게 코드를 묻기 전에는 합치지 않는다.

**데모.** MVP 는 국가 하나, 직접 구매(깊이 1)만. 150분 이후 깊이 2~3. 뉴스 수집은 하지 않는다. 국가 목록은 사용자가 넣는 조건 JSON.

**검증.** 국가가 아닌 기업은 깊이 0에 없어야 한다. 국적 빈 값 건수를 화면에 남긴다. 손계산 표본은 기업 5곳.

**이 저장소.** `propagate` 를 실패 집합으로 확장하는 자리. 온톨로지 Location, Risk event.

## 4. 협력사명 표기 불일치 (entity resolution)

**문제 한 줄.** 같은 회사로 보이는 이름 표기를 묶어, 묶기 전후 거래 금액 합이 같은지 보여 준다.

**현업 맥락.** 구매 시스템, 공시, 엑셀의 사명이 다르다. `(주)`, 영문, 공백, 오타 때문에 단일 공급처가 두 회사로 갈라져 위험이 숨는다.

**입력 데이터.** company name, 별칭 열이 있으면 그것, transactions 의 id. id 가 이미 같으면 이름을 합치지 않는다.

**정식화.** 규칙만 쓴다. 공백·`(주)`·`㈜`·`주식회사` 제거, 영문 소문자, 그다음 완전 일치. 편집 거리나 임베딩은 개선이고, 자동 병합은 하지 않고 후보 쌍만 낸다. 사람이 고른 쌍만 id 를 합친다.

**데모.** MVP 는 정규화 키가 같은 이름 그룹과, 그룹별 금액 합. 애매한 쌍은 후보 표. 학습 모델과 외부 검색은 안 한다.

**검증.** 정규화 전후 금액 총합이 같다. `(주)가짜웨이퍼` 와 `가짜웨이퍼(주)` 는 같은 키. `가짜웨이퍼` 와 `가짜가스` 는 자동 병합되지 않는다.

**이 저장소.** 알고리즘 문서의 엔티티 절. graph_ref 는 id 가 정리된 뒤를 가정하므로, 병합은 그 앞 단계로 따로 둔다.

## 5. 거래처 집중도와 협상력

**문제 한 줄.** 구매자·자재(또는 구매자 전체)의 공급 집중도 HHI 를 계산하고, 높은 순으로 협상 우선순위를 매긴다.

**현업 맥락.** 한 곳에 금액이 몰리면 단가 협상력이 없다. TL 은 HHI 와 1위 비중을 같이 보고 협상 대상을 고른다.

**입력 데이터.** transactions.amount. 물량이 없고 금액만 있으면 금액 비중이라고 적는다. 둘 다 있으면 담당자에게 어느 쪽으로 집중도를 볼지 묻는다.

**정식화.** 비중 s_i = 금액_i / 합. HHI = Σ s_i^2 (0~1). 독점이면 1, 균등 n 곳이면 1/n. 경쟁당국식 0~10000 은 개선으로 HHI*10000 열만 추가. 정렬은 HHI 내림차순, 동률이면 금액 합, 그다음 buyer_id.

**데모.** MVP 는 구매자·자재별 HHI 표. 150분 이후 1위 공급처와 비중. "협상력 점수" 같은 새 공식은 만들지 않는다.

**검증.** 50:50 이면 0.5, 100:0 이면 1, 80:20 이면 0.68 을 손계산과 비교. 합이 0이면 HHI 를 비우고 사유를 적는다. 검사기가 금액을 다시 더해 비중이 1인지 본다.

**이 저장소.** `graph_ref.py` 의 `concentration`. `$data-judge` 로 기준표(높음 기준)를 확정한 뒤 코드에 둔다.

## 6. 2차·3차까지 숨은 의존

**문제 한 줄.** 1차 협력사 너머, 그 협력사의 공급자가 멈추면 우리 자재가 막히는지 깊이 2~3만 추적한다.

**현업 맥락.** 1차 다변화가 되어 있어도 2차가 한 곳이면 위험은 같다. TL 은 계약 상대가 아닌 기업의 이름을 보고 싶어 한다.

**입력 데이터.** 문제 1과 같음. "우리" 회사 id 는 담당자에게 확인. 데이터에 없으면 구매만 하고 공급은 하지 않는 노드를 우리 쪽으로 두는 안을 가정으로 적고 확인 필요로 남긴다.

**정식화.** 문제 1의 BFS 에서 시작점을 우리 회사의 직접 공급자가 아니라, 사용자가 지정한 중단 기업으로 둔다. 깊이는 기본 3에서 자른다. 깊이 상한과 같으면 포함하고 그 이상은 버린다.

**데모.** MVP 는 깊이 2. 150분 이후 깊이 3과 잘린 노드 수. 전체 최단경로 그림, Neo4j 는 하지 않는다.

**검증.** 순환(A→B→A)에서 방문 노드가 한 번만 나오는지. 깊이 3과 4의 경계. 검사기는 부모 맵으로 깊이를 다시 센다.

**이 저장소.** `propagate` 의 max_depth. 온톨로지의 공급 간선.

## 7. 이상 거래·단가 급변

**문제 한 줄.** 같은 구매자·공급자·자재의 기간별 단가(또는 금액)가 직전 기간 대비 기준 이상 오르면 사유와 함께 표시한다.

**현업 맥락.** 갑작스러운 단가 인상은 품질 이슈, 환율, 또는 입력 오류다. TL 은 자동 경보로 원인을 묻는 목록을 원한다. 오탐이 많아도 놓치는 것보다는 낫다고 가정하고 담당자에게 확인한다.

**입력 데이터.** transactions 에 period, amount, 가능하면 qty. 단가 = amount/qty. qty 가 없으면 금액만 보고 단가라고 말하지 않는다.

**정식화.** 기간을 정렬해 직전 대비 증가율. 기준(예: 30%)은 담당자 답. 같으면 포함한다(>=). 직전 금액이 0이면 비율 대신 `확인 필요`. 평균·표준편차는 기간이 4개 이상일 때만 개선.

**데모.** MVP 는 직전 대비 증가율 표와 기준 초과 행. 그래프 지표는 붙이지 않는다. `$data-judge` 의 행마다 사유.

**검증.** 기준과 같은 행, 바로 아래, qty 0, 기간 한 줄뿐인 쌍. 제외 행 수와 금액 합을 전후로 출력.

**이 저장소.** 알고리즘 문서 이상 탐지 절. graph_ref 범위 밖이면 당일 작은 함수로 새로 짠다.

## 8. 신규 협력사 후보와 유사 기업

**문제 한 줄.** 한 자재를 공급하는 기업 중 우리와 거래가 없는 곳을, 이미 쓰는 공급사와 겹치는 자재 수로 정렬한다.

**현업 맥락.** 단일 소싱을 줄이려면 후보가 필요하다. TL 은 "같은 업종·같은 자재를 이미 시장에 파는 곳"을 짧게 보고 평가 착수 여부를 정한다. 점수가 합격은 아니다.

**입력 데이터.** transactions.product, companies.industry. 재무 데이터가 없으면 재무 평가는 하지 않는다고 적는다.

**정식화.** 자재 집합의 Jaccard = 교집합/합집합. 우리 기존 공급사들과의 Jaccard 최댓값을 점수로 하고, 동률이면 industry 일치, 그다음 id. 거래 이력이 없으면 점수 0과 사유.

**데모.** MVP 는 자재 하나를 고르면 미거래 공급사 목록. 150분 이후 Jaccard. 추천 문장은 템플릿. 클러스터링 알고리즘은 안 한다.

**검증.** 자재가 완전히 같으면 1, 겹침이 없으면 0. 이미 거래 중인 기업은 후보에서 빠진다. 손계산 3사.

**이 저장소.** 알고리즘 문서 유사도 절. `alternatives` 는 금액 정렬의 단순판이므로, Jaccard 는 그 다음에 따로 둔다.

## 9. 공시·뉴스 기반 재무 위험 조기경보

**문제 한 줄.** 이미 받은 협력사 재무 표에서 적자, 자본잠식, 매출 급감 규칙을 적용해 경보 목록을 만든다.

**현업 맥락.** TL 은 뉴스를 직접 읽기 전에, 숫자 조건에 걸린 협력사만 보고 싶다. 기사 원문 수집은 6시간 밖에 둔다. 입력이 표로 와 있다고 가정하고, 없으면 안 할 일로 올린다.

**입력 데이터.** `financials.csv`: company_id, period, revenue, operating_income, equity. 없는 열은 그 규칙을 끄고 사유를 적는다.

**정식화.** 규칙 표. 예: 영업이익 < 0, 자본 <= 0, 매출이 직전 대비 기준 이하. 같으면 경보에 포함할지는 담당자 확인. 뉴스 문장 분류가 필요하면 `$llm-feature`: 규칙이 먼저, LLM 은 문구, 키 없으면 규칙 문장만.

**데모.** MVP 는 규칙 두 개의 경보 표. 뉴스 API, 스크래핑은 하지 않는다. 샘플 문장이 파일로 오면 키워드 포함만 개선으로.

**검증.** 0, 음수, 빈 칸을 구분한다. 빈 칸을 0으로 채우지 않는다. 행 수 = 경보 + 정상 + 확인 필요.

**이 저장소.** `$data-judge`, 온톨로지 Financial metrics. graph_ref 와 섞지 않고 표를 먼저 판정한 뒤 company_id 로 그래프에 붙인다.

## 10. 조건이 바뀌면 조달 계획 재분석

**문제 한 줄.** "거래처 A 부도", "국가 X 수출통제", "단가 상한 변경" 문장을 조건 JSON 으로 바꾸고, 이전 결과와 달라진 기업·자재만 보여 준다.

**현업 맥락.** 회의 중에 조건이 바뀐다. TL 은 처음부터 다시 설명하지 않고, 빠진 공급과 새로 단일 소싱이 된 자재만 본다.

**입력 데이터.** 문제 1의 CSV 와 조건 JSON. 예: `{"type":"supplier_failure","company_id":"B"}`, `{"type":"country_control","country":"ZZ"}`, `{"type":"price_cap","product":"wafer","max_unit_price":1000}`.

**정식화.** 문장 → JSON 은 규칙(키워드와 ID). LLM 은 키가 있을 때만 쓰고, 출력은 허용 type 과 필수 키를 검사한다. 실패하면 규칙 결과 또는 오류. 재분석은 그래프를 복사해 간선을 제거하거나 단가 초과 간선을 뺀 뒤 문제 2·5를 다시 계산한다. diff 는 이전 집합과 이후 집합의 추가·삭제.

**데모.** MVP 는 JSON 을 직접 넣어 재계산. 150~240분에 문장 규칙과 diff. LLM 호출은 키가 있을 때만 개선이고, 테스트는 네트워크 없이 가짜 응답으로 한다.

**검증.** 같은 JSON 은 같은 diff. 알 수 없는 type 은 적용하지 않고 오류. 부도 전후 단일 공급처 개수가 손계산과 같다. 이전 결과를 덮어쓰지 않는다.

**이 저장소.** `templates/agent/` 가 있으면 그 규칙 파서. 없으면 당일 50줄 이하로 새로 만든다. `$llm-feature`, `$graph-analysis`.
